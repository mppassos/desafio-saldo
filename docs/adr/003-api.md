# ADR 003 — API de Consulta de Saldo

- **Status:** Aceito
- **Data:** Julho/2026

## Contexto

O desafio exige expor um endpoint REST que, dado o identificador da conta
(UUID), retorne o saldo mais atual com: `id`, `owner`, `balance`
(`amount` + `currency` ISO 4217) e `updated_at` (ISO 8601 com offset).
O contrato de exemplo do enunciado usa **snake_case** (`updated_at`).

## Decisões

### D1. Endpoint e versionamento

`GET /api/v1/balances/{accountId}` — o prefixo `/api/v1` versiona o contrato
no path (a quebra de contrato futura fica explícita na URL, sem quebrar
clientes antigos). O `accountId` é convertido pelo Spring para `UUID`;
valor inválido resulta em **400** (e não 500).

### D2. Contrato snake_case (alinhado ao enunciado)

`spring.jackson.property-naming-strategy: SNAKE_CASE` global: `updatedAt`
(Java) é serializado como `updated_at` (JSON), idêntico ao payload e à
resposta do desafio. DTOs são **Java records** (imutáveis, concisos).

### D3. `updated_at` = timestamp da transação, com fuso explícito

O valor vem do `updated_at` do saldo (que o ingestor grava com o timestamp
da mensagem em microssegundos) e é formatado com `ISO_OFFSET_DATE_TIME` no
fuso configurado (`app.timezone`, default `America/Sao_Paulo`) — ex.:
`2025-07-05T18:04:13.433-03:00`. Nunca usamos `ZoneId.systemDefault()`
(a serialização não pode depender do fuso da máquina).

### D4. Erros padronizados

Corpo de erro único (`ErrorResponse`) com `timestamp`, `status`, `error`,
`message`, `path`:

| Status | Quando |
|---|---|
| 200 | saldo encontrado |
| 400 | `accountId` não é UUID válido / corpo ilegível |
| 404 | conta inexistente (`AccountNotFoundException`) |
| 500 | erro não tratado — **logado com pilha completa**, corpo genérico (sem vazar detalhes) |

`@RestControllerAdvice` centraliza o mapeamento.

### D5. Leitura simples e stateless

Duas consultas por PK (`accounts`, `balances`), sem N+1 (busca por id único),
`@Transactional(readOnly = true)`. A API **não escreve** — o ingestor é o
único escritor. Health check via Spring Actuator (`/actuator/health`) para
os target groups do load balancer e a validação do Blue/Green.

## Consequências

**Positivas**

- Contrato idêntico ao enunciado (facilita a avaliação automatizada/manual);
- Erros previsíveis e documentados (Swagger via springdoc);
- Deploy/rollback independentes da API (stateless, read-only).

**Negativas / trade-offs**

- Duas queries por chamada: em leitura pesada, o próximo passo é cache Redis
  ou réplica de leitura (roadmap) — o custo atual é aceitável para o desafio;
- Versionamento por path é pragmático, mas menos "limpo" que content
  negotiation (padrão aceito na indústria).
